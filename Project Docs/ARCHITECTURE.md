# Architecture

This describes the **actual current implementation** — a local Postgres database, a bare Express/TypeScript backend scaffold, and Prisma Client connected to it, per Phases 1–3 — followed by the **planned** architecture per the chosen production stack for everything not yet built. See `DECISIONS.md` for the reasoning behind decisions already made, and `TASKS.md` for what's still open.

## System Overview

**Implemented:** A local PostgreSQL 18 database (`daymark_ledger_dev`, see Phase 1 in `PHASES.md`), an Express 5 + TypeScript backend (`backend/`, see Phase 2 in `PHASES.md`) with a `GET /health` liveness endpoint, a `GET /api/db-check` endpoint (Phase 6) proving DB connectivity via a raw Prisma query, a real auth backend (Phase 7): `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`, and session-verification middleware, backed by Prisma's first real migration (`User`/`Session` models), the first domain models (Phase 9): `Worker`/`Attendance`, with `GET /api/workers` (active workers + today's status) and `POST /api/workers/:id/attendance/today` behind session auth, the second domain migration (Phase 11, `Advance`) plus any-date attendance get/set and salary/advance calculation endpoints, and — as of Phase 12 — a single-worker identity endpoint, a full attendance-history list endpoint, and a per-day-rate update endpoint, and — as of Phase 13 — a create-worker endpoint (see "API Architecture" below). As of Phase 20a/20b (2026-09-23), an `AdvanceRepayment` model tracks repayments tagged against one of two independent buckets (MONTH/YEAR), with `GET /api/workers/:id/advance-overview`, `GET /api/workers/:id/repayments/:bucket`, and `POST /api/workers/:id/repayments` endpoints; `computeSalaryTotals()`'s `remainingOwed` and a new `computeAdvanceOverview()` both net repayments against advances. Prisma (CLI + Client, see Phases 3–4, 7, 9, 11 in `PHASES.md`) is installed, connected to that database via a Postgres driver adapter, with its CLI tooling (`generate`/`validate`/`format`/`migrate dev`/`migrate status`/`studio`/`seed`) fully verified via `backend/package.json`'s `prisma:*` scripts. A React 19 + Vite 8 + TypeScript + Tailwind CSS v4 frontend (`frontend/`, see Phase 5 in `PHASES.md`) has a real, working login screen wired to the Phase 7 backend, `react-router-dom`-based routing, a Context-based auth state (Phase 8), a real mobile-first home screen (Phase 10, worker list with inline today-status change, a floating quick-actions menu) wired to the Phase 9 API, a real Worker Detail screen (Phase 12, monthly attendance calendar, a day-edit popup, salary configuration, calculated totals, advance history) wired to the Phase 11 API, and — as of Phase 14 — a real Create New Employee form wired to the Phase 13 API, all matching the UI prototype's visual design. As of Phase 20a/20b, the Worker Detail screen's "REMAINING OWED" tile links to a dedicated `AdvanceDetailsScreen` (`/workers/:id/advance-details`) showing per-bucket advance/repaid/outstanding figures, a repayment input + Save per bucket, and collapsible history. The full frontend → backend → database → backend → frontend round trip (Phase 6) is proven, gated behind real authentication end-to-end, and now serving real domain data across three full screens. Only the home screen's Create New Employee quick-actions entry is wired up; Manage Employees, Reporting, and Settings entries remain non-functional placeholders and their screens don't exist yet (Phase 15a+). The repository also contains this `Project Docs/` documentation system and a `Prototype/` folder (see "Prototype" below).

**Prototype (2026-09-18, not production code):** An interactive, non-functional UI prototype — a mobile view (390×844), built as a Claude Artifact (Design Component format, `<x-dc>`/`DCLogic`, not React/Vite) — lives at `Prototype/project/Main.dc.html` in this repo, with the live/editable version linked from `Prototype/README.md`. It uses in-memory sample data only (no backend, no persistence) and exists purely to validate the UX before real implementation. Screens covered: Worker List (home, with inline today-status change), Worker Detail (attendance calendar, salary config, salary/advance totals, advance history), a floating quick-actions menu, Manage Employees List, Manage Employee Edit (Active/Inactive toggle, personal-info edit, document add/remove), Create New Employee, and placeholder "coming soon" screens for Reporting and Settings (not yet designed — see `TASKS.md`). This prototype's screen/data shape should inform, but does not replace, the real Prisma schema and API design once implementation starts.

**Planned:** A normal client-server web app — a React frontend talking to a Node/Express REST API backend, backed by a PostgreSQL database — gated by a dedicated login screen, accessible from any device with internet access (not an offline-only/local-storage app; see `DECISIONS.md`'s production stack decision). Provides a per-worker module (profile, monthly attendance calendar, salary configuration, auto-calculated salary/advance totals) plus a separate Manage Employees flow (see `PROJECT.md` for the full feature set, and DECISIONS.md's prototype navigation decision).

## Technology Stack

- **Frontend (implemented, Phases 5–6, 8, 10, 12):** React 19 + Vite 8 + TypeScript, scaffolded at `frontend/` via `npm create vite@latest frontend -- --template react-ts`, run via npm scripts (`dev`, `build` via `tsc -b && vite build`, `preview`). Tailwind CSS v4 wired in via the `@tailwindcss/vite` plugin — CSS-first config, no `tailwind.config.js`/`postcss.config.js` (see `DECISIONS.md`); a `@theme` block in `index.css` carries the app-wide brand tokens (teal primary, warm stone neutrals, Manrope font, plus Present/Half/Absent status-color tokens added in Phase 10 — all matching the prototype, used by `HomeScreen` and, as of Phase 12, `AttendanceCalendar`/`DayEditPopup`/`EarningsSummaryCard`) plus a second, screen-scoped set of navy tokens (`--color-login-header-start/-end`, `--color-login-accent`) used only by `LoginScreen`, whose visual design was rebuilt to match an owner-supplied mobile mockup rather than the app-wide prototype brand (see Phase 8's note in `PHASES.md`). `react-router-dom` provides routing (`/login`, `/`, `/workers/:id`), and a Context-based `AuthProvider` (see "Authentication & Authorization" below) tracks session state, checking `GET /api/auth/me` once on mount. `App.tsx`'s Phase 6 `/api/db-check` demo fetch has been removed (superseded by the real login flow); the Phase 8 `HomePlaceholder` has been removed (superseded by Phase 10's real `HomeScreen`); the Phase 10 `WorkerDetailStub` has been removed (superseded by Phase 12's real `WorkerDetailScreen`). `pdfjs-dist` (added 2026-09-20) renders uploaded PDF documents to a `<canvas>` in `PdfViewer.tsx`, dynamically imported so its ~430KB stays out of the main bundle until a PDF is actually previewed.
- **Backend (implemented, Phases 2, 6, 9):** Node.js + **Express 5** + TypeScript, exposing a REST API, run via npm scripts (`dev` via `tsx watch`, `build` via `tsc`, `start` via compiled `dist/`). CORS is enabled via the `cors` package, allow-listing an origin (`CORS_ORIGIN` env var, defaults to `http://localhost:5173`), but is currently unused by local dev — the frontend's Vite dev-server proxy (see below and `DECISIONS.md`) makes requests same-origin from the browser's perspective, so no cross-origin request actually occurs in dev. The CORS middleware is left in place for direct/cross-origin access (e.g. non-browser clients, or a future production topology) rather than removed. Next.js is explicitly not part of the default stack — see `DECISIONS.md` for the condition under which it could be introduced later. `multer@^2.4.0` (Phase 15b) handles multipart file uploads for worker documents/photos, writing to local disk (see "Data / Persistence" and `DECISIONS.md`'s storage decision). `pdfmake` and `exceljs` (Phase 18) generate the downloadable attendance-register report files server-side — no headless browser dependency (see `DECISIONS.md`'s report-generation decision); pdfmake's server API is covered by a small local ambient declaration (`backend/src/types/pdfmake.d.ts`) since the published `@types/pdfmake` targets an older, incompatible pdfmake API.
- **Database (implemented, Phase 1):** PostgreSQL 18, local dev database `daymark_ledger_dev` on the native Windows service.
- **ORM (implemented, Phases 3–4, 7, 9, 11):** Prisma 7.10.0 (CLI + `@prisma/client`, pinned to matching versions), connected to Postgres via `@prisma/adapter-pg` (this Prisma version requires an explicit driver adapter — no built-in engine-binary connection). Config lives in `prisma7.config.ts` (not `schema.prisma`'s `env()`, per this version's setup) and is auto-discovered by the CLI despite its non-default filename. `backend/package.json`'s `prisma:validate`/`prisma:format`/`prisma:generate`/`prisma:migrate:dev`/`prisma:migrate:status`/`prisma:studio`/`prisma:seed` npm scripts wrap the CLI (each pinned to `--config prisma7.config.ts` for self-documentation) and are all confirmed working end-to-end against `daymark_ledger_dev`. Schema has `User`/`Session` (Phase 7), `Worker`/`Attendance` (Phase 9), `Advance` (Phase 11), and `WorkerDocument` (Phase 15b, see "Data / Persistence" below).
- **Auth (implemented, Phase 7):** Database-backed sessions (SHA-256-hashed session token) + bcrypt-hashed account password (cost factor 12), a single seeded admin account. See "Authentication & Authorization" below.
- **Hosting/PaaS:** Not yet chosen — see `TASKS.md`.

## Application Structure

**Monorepo** (single git repo, resolved by Phase 2): top-level `backend/` (Express + TypeScript, scaffolded) and `frontend/` (React/Vite, scaffolded Phase 5) directories, communicating over a REST API (first round trip proven Phase 6). No npm workspaces/build-orchestration tool (e.g. Turborepo) — each app has its own standalone `package.json`; revisit only if a concrete cross-package sharing need arises.

`backend/` layout (as of Phase 15b):
```text
backend/
  src/
    index.ts               — Express app bootstrap; GET /health (liveness), GET /api/db-check (Phase 6), mounts /api/auth (Phase 7), the Phase 18 reports router, /api/workers (Phase 9), the Phase 11 advances router, the Phase 20a repayments router, and the Phase 15b documents router (all under /api/workers, reports mounted before workers — see routes/reports.ts's note on why the order matters; repayments' routes all have a second path segment, e.g. /:id/repayments, so mount order relative to workers' /:id doesn't create the same shadowing risk); express.json()/cookieParser() wired in
    db.ts                   — Prisma Client singleton (PrismaClient + @prisma/adapter-pg)
    lib/
      auth.ts                — bcrypt hash/compare, session token generation + SHA-256 hashing, cookie name/options
      date.ts                 — todayDateOnly(): the server's local calendar date anchored at UTC midnight, for @db.Date columns (Phase 9); parseDateOnly()/dateOnlyToString() (Phase 11): parse/serialize an arbitrary YYYY-MM-DD route param using the same UTC-midnight anchoring, rejecting malformed/overflow dates
      salary.ts               — computeSalaryTotals() (Phase 11): pure function (no Express/Prisma imports) applying the flat half-day rule and summing all-time gross/net earned plus month/year/all-time advance totals; as of Phase 20a takes a repayments array and nets remainingOwed = all-time advances − all-time repayments
      repayment.ts             — (Phase 20a) computeAdvanceOverview(): pure function computing per-bucket (MONTH/YEAR) advanceTaken/repaid/outstanding plus a netted totalAdvance, from a worker's advances and MONTH-/YEAR-tagged repayments
      storage.ts               — workerUploadDir()/ensureWorkerUploadDir()/generateStoredFileName() (Phase 15b): local-filesystem upload path construction, directory creation, and random-UUID-based stored filenames that never trust a client-supplied original filename on disk
      reportColumns.ts          — (Phase 18) backend-owned copy of the 10 ReportFieldKey/labels matching frontend/src/types/report.ts verbatim (no cross-package import), plus daysInMonth()/REPORT_MONTH_NAMES and orderedActiveFields()
      reportData.ts             — (Phase 18) enumerateMonthSections() splits an arbitrary [from,to] range into one entry per calendar month touched; assembleReportData() runs 3 batched Prisma queries (no N+1) and reuses the existing computeSalaryTotals() per worker × per month section
      reportPdf.ts               — (Phase 18) buildReportPdfDocDefinition(): pdfmake docDefinition, A3 landscape, a custom bordered "ledger" table layout applied unconditionally, 31 fixed day-columns inserted only when the attendance field is active
      reportExcel.ts             — (Phase 18) buildReportWorkbook(): exceljs workbook, one worksheet per month section with a frozen header row and matching bordered-grid cell styling
    types/
      pdfmake.d.ts             — (Phase 18) local ambient declaration for pdfmake's server API (createPdf/getBuffer/setFonts) — the published @types/pdfmake targets an older, incompatible browser-bundle API
    middleware/
      requireSession.ts      — reads the session cookie, validates it against the Session table, attaches req.user or responds 401
    routes/
      auth.ts                 — POST /login, POST /logout, GET /me
      reports.ts               — (Phase 18) POST /report: validates format/from/to/fields/workerIds, generates the PDF/Excel file fully into an in-memory buffer, responds with a binary file (Content-Disposition: attachment) — the one route in this codebase whose success response isn't the {status,message} envelope; GET /report-preferences (list, sorted by name) and POST /report-preferences (create — name + a normalized full 10-key fields object, see DECISIONS.md) added in a 2026-09-21 refinement for the Field Preference feature, scoped to Fields to Include only, no update/delete
      workers.ts               — GET / (active workers + today's status); POST / (Phase 13, create worker — fullName/designation/contact/joiningDate/perDayRate, always created ACTIVE); GET /all (Phase 15a, every worker Active + Inactive — id/fullName/designation/status only, for the future Manage Employees List screen); GET /:id (identity incl. contact/joiningDate as of Phase 15b: fullName/designation/contact/joiningDate/perDayRate/status); POST /:id (Phase 15b, update fullName/designation/contact/joiningDate — excludes perDayRate/status, each with their own endpoint); POST /:id/status (Phase 15b, explicit {status: ACTIVE|INACTIVE} toggle); POST /:id/delete (2026-09-21 refinement, 400 unless the worker is currently INACTIVE, else prisma.worker.delete() cascades Attendance/Advance/WorkerDocument rows and the route also best-effort-removes the worker's uploads/<id>/ directory from disk — see DECISIONS.md's worker-lifecycle-reversed entry); POST /:id/attendance/today (Phase 9); GET/POST /:id/attendance/:date (Phase 11, any-date get/set, sharing a setAttendanceForDate() helper with /today); GET /:id/attendance (Phase 12, full history list, mirrors advances.ts's GET /:id/advances); GET /:id/salary-summary (Phase 11; takes required year/month query params as of the month-scoping decision below, defaulting to the real current month/year when both are omitted); POST /:id/rate (Phase 12, updates perDayRate — see DECISIONS.md's rate-editing-pulled-forward entry)
      advances.ts               — POST /:id/advances/:date (upsert, or clears the day's entry when amount is 0/null) and GET /:id/advances (history, date descending) (Phase 11)
      repayments.ts             — (Phase 20a) GET /:id/advance-overview (netted totalAdvance plus per-bucket advanceTaken/repaid/outstanding), GET /:id/repayments/:bucket (history for MONTH or YEAR, date then createdAt descending), POST /:id/repayments ({bucket, amount} — validates the bucket, requires a positive amount, blocks the repayment with a 400 if it would exceed that bucket's current outstanding balance, and returns both the created repayment and the recomputed overview)
      documents.ts               — POST /:id/documents (Phase 15b, multipart upload via multer — pdf/jpg/jpeg/png allow-list, 10MB limit, manual multer-callback invocation to translate errors into this codebase's {status:"error"} envelope); GET /:id/documents (list, newest first); GET /:id/documents/:documentId/download (streams the file back, scoped to its owning worker; Content-Disposition changed from attachment to inline in a 2026-09-20 refinement so the frontend's <img>/PdfViewer can render it directly instead of forcing a download); POST /:id/documents/:documentId/remove (deletes the DB row and best-effort-unlinks the disk file)
    generated/prisma/      — generated Prisma Client (gitignored, regenerated via `prisma generate`)
  prisma/
    schema.prisma          — User, Session, Worker, Attendance, Advance (Phase 11), WorkerDocument (Phase 15b), ReportFieldPreference (Phase 18 refinement, `fields` as Json), AdvanceRepayment + RepaymentBucket enum (MONTH | YEAR, Phase 20a — bucket is permanently set at creation, never re-derived from date) models
    seed.ts                 — seeds the admin user (ADMIN_USERNAME/ADMIN_PASSWORD) and sample workers/Attendance/Advance rows — no create-worker endpoint existed when this was first written, so the seed count is stale relative to the live database (see Phase 15a's note in PHASES.md); dates are relative to the real current date
    migrations/              — add_user_session, add_worker_attendance, add_worker_advance, add_worker_document, add_report_field_preference, add_advance_repayment (Phase 20a)
  uploads/                 — local-disk storage for worker documents/photos, backend/uploads/<workerId>/<generated-filename> (gitignored, Phase 15b — see DECISIONS.md's storage decision)
  prisma7.config.ts        — Prisma config (schema path, migrations path + seed command, datasource URL from env)
  .env                     — local env vars incl. DATABASE_URL, CORS_ORIGIN, ADMIN_USERNAME, ADMIN_PASSWORD (gitignored)
  .env.example             — committed template (PORT, CORS_ORIGIN, DATABASE_URL shape, ADMIN_USERNAME/ADMIN_PASSWORD placeholders)
  package.json
  tsconfig.json
```

## Data Flow

**Today's attendance, any-date attendance/advances, and calculated totals all implemented end-to-end (Phases 9–12):** Tapping a status pill on the home screen sends `POST /api/workers/:id/attendance/today` immediately (no confirmation dialog, matching the prototype), which the backend persists via an upsert on `Attendance`'s `(workerId, date)` unique key — updating that day's record in place rather than creating duplicates. Tapping the currently-active pill again sends `status: null`, which the backend treats as "clear today's record" (deletes the row rather than storing a null status). The frontend applies the change optimistically (updates local state immediately, reverting only if the request fails) rather than waiting on a refetch. Phase 11 generalized this same upsert/clear pattern to `POST /api/workers/:id/attendance/:date` for any date, and added the equivalent for advances: `POST /api/workers/:id/advances/:date` upserts that day's single advance amount, or clears it (deletes the row) when the amount is `0`/`null` — mirroring the Attendance clear behavior, per `DECISIONS.md`'s Advance-uniqueness decision (one advance per worker per day, not an append-only ledger). Phase 12's `WorkerDetailScreen` wires the day-edit popup to both endpoints via a single `Promise.all` on Save (they're independent calls — no combined endpoint exists), then optimistically patches its local attendance/advance arrays and separately re-fetches just `GET /:id/salary-summary` for the currently displayed month/year (the half-day/month/year math already lives correctly server-side, so the frontend doesn't duplicate it). Editing a worker's per-day rate (`SalaryConfigCard`, save-on-blur) posts to `POST /api/workers/:id/rate` and likewise triggers a `salary-summary` re-fetch, since the backend always computes totals from the worker's *current* rate applied across the target month's attendance (not a rate-at-the-time-of-entry model) — changing the rate retroactively changes that month's gross/net figures too, by design. All salary and advance totals are computed server-side by `GET /api/workers/:id/salary-summary` (Phase 11, via `lib/salary.ts`'s `computeSalaryTotals()`), never entered directly. As of the month-scoping decision in `DECISIONS.md`, gross earned, net earned, and this-month advance are scoped to whichever `year`/`month` the endpoint is called with (`WorkerDetailScreen` passes the calendar's currently displayed month, refetching on every month-nav), this-year advance is scoped to that month's year, and remaining owed stays an all-time running total.

**Auth, home-screen, Worker Detail, Create Employee, Manage Employees, Reporting, and Inactive Employees backend endpoints are all implemented and consumed by the frontend (Phases 7–18 plus post-completion refinements) — Settings was cancelled and has no endpoints:** A REST API served by the Express backend, CORS-enabled for the frontend's origin (with `credentials: true` so the session cookie is sent). `GET /health` (Phase 2, liveness only), `GET /api/db-check` (Phase 6), `/api/auth/login` / `/api/auth/logout` / `/api/auth/me` (Phase 7), `GET /api/workers` / `POST /api/workers/:id/attendance/today` (Phase 9), `GET`/`POST /api/workers/:id/attendance/:date` (any-date get/set, Phase 11), `GET /api/workers/:id/salary-summary` (calculated totals, Phase 11; Phase 20a added `GET /api/workers/:id/advance-overview` (netted `totalAdvance` plus per-bucket `advanceTaken`/`repaid`/`outstanding` for `MONTH` and `YEAR`), `GET /api/workers/:id/repayments/:bucket` (that bucket's dated repayment history), and `POST /api/workers/:id/repayments` (`{bucket, amount}` — 400s if the amount would exceed that bucket's current outstanding balance, otherwise creates the repayment and returns it alongside the recomputed overview) on a new `repaymentsRouter`, mounted at `/api/workers`.

**Connection implemented (Phase 3); User/Session schema (Phase 7), Worker/Attendance (Phase 9), Advance (Phase 11), and WorkerDocument (Phase 15b) implemented:** PostgreSQL 18 (`daymark_ledger_dev` locally), accessed via Prisma Client + `@prisma/adapter-pg`, confirmed connecting successfully. Phase 11's migration (`add_worker_advance`) added `Advance` (`workerId` FK with cascade delete, `date` as `@db.Date`, `amount` as `Decimal(10,2)`, `@@unique([workerId, date])` so each worker has at most one advance per calendar day — see `DECISIONS.md`'s Advance-uniqueness decision — plus `@@index([date])`). ## Authentication & Authorization

**Implemented (Phase 7):** A single admin account, seeded via `backend/prisma/seed.ts` from `ADMIN_USERNAME`/`ADMIN_PASSWORD` env vars (no hardcoded credentials). `POST /api/auth/login` checks the submitted password against the bcrypt hash (cost factor 12) stored on `User.passwordHash`; on success, a random 32-byte session token is generated, its SHA-256 hash + a 30-day `expiresAt` are stored on a new `Session` row (never the raw token — satisfies the "hashed before storage" requirement), and the raw token is set as an httpOnly cookie (`sameSite: lax`, `secure` in production only) for the client to hold. `GET /api/auth/me`, behind the `requireSession` middleware, hashes the incoming cookie token and looks it up against `Session` to authenticate a request. `POST /api/auth/logout` deletes the matching `Session` row and clears the cookie. This is deliberately not a stateless JWT approach — a database-backed session allows the session to be revoked/invalidated server-side at any time (e.g. logout deletes the row immediately). No worker-facing accounts, no multi-admin support, no OAuth/social login. **Frontend (Phase 8):** `AuthContext`/`AuthProvider` checks `GET /api/auth/me` once on mount (so a page reload doesn't force re-login within the 30-day session), and `LoginScreen`/`HomePlaceholder` call `login()`/`logout()` against the Phase 7 endpoints; `RequireAuth` gates the placeholder home route. Not yet built: applying `requireSession` to future business routes (Phase 9+).

## Important Invariants

These hold regardless of further implementation detail, since they come directly from the specification (`PROJECT.md`) and the production stack decision (`DECISIONS.md`):

- Half-day pay is always exactly **0.5 × the per-day rate** — a flat rule applied identically to every worker, not configurable per worker.
- An **Active** worker is never deleted directly — a worker who stops working must first be marked Inactive; reactivating an Inactive worker later must preserve all prior attendance/salary/advance history intact. As of a 2026-09-21 reversal (see `DECISIONS.md`), an **Inactive** worker *can* be permanently deleted (`POST /api/workers/:id/delete`, via the Inactive Employees screen) — this is real, irreversible deletion, cascading all their attendance/advance/document history.
- Attendance must be editable for **any date**, past or present — backfilling/correcting a prior day's status is a core requirement, not an edge case to special-case away.
- Advance salary is logged as **individual dated entries** (date + amount) — never collapsed into or replaced by a single manually-edited running-balance field.
- All salary/advance totals shown to the admin are **auto-calculated** from attendance and advance entries — never a manually-entered figure.
- This is a hosted client-server app, not an offline-only tool — the frontend requires connectivity to the backend API to function. Do not reintroduce local-only storage (e.g. IndexedDB as the source of truth) without an explicit owner decision superseding the production stack decision in `DECISIONS.md`.
- Sessions are database-backed with a hashed session ID, and the account password is bcrypt-hashed — never store either in plaintext, and never switch to stateless JWTs without an explicit owner decision, since revocability was the deliberate reason for this choice.
